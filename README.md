# 🧮 Mini NPU Simulator

AI가 이미지를 판별할 때 쓰는 가장 기본적인 연산인 **MAC(Multiply-Accumulate)** 을 Python 반복문으로 직접 구현한 콘솔 프로그램입니다.
입력 패턴이 십자가(Cross)인지 X인지 판정하고, 패턴 크기(3×3 ~ 25×25)에 따라 연산 시간이 어떻게 늘어나는지 측정합니다.

---

## 1. 개요

| 항목 | 내용 |
|---|---|
| 핵심 원리 | 패턴과 필터를 겹쳐 **같은 위치끼리 곱하고(Multiply) 모두 더한(Accumulate)** 값을 유사도 점수로 사용 |
| 판정 방식 | Cross 필터 점수와 X 필터 점수를 비교해 큰 쪽으로 판정. 차이가 `1e-9` 미만이면 동점(UNDECIDED) |
| 지원 크기 | 3×3(직접 입력), 5×5 / 13×13 / 25×25(data.json), 3~51(패턴 생성기) |
| 개발 환경 | Windows 11, Python 3.14에서 실행 확인. 과제 조건(Python 3.8 이상)에 맞춰 3.9 이후에 추가된 문법·함수는 쓰지 않았습니다. 표준 라이브러리만 사용합니다 (`json`, `time`, `math`, `re`, `pathlib`, `unicodedata`). |
| 외부 라이브러리 | 사용하지 않음 (NumPy, pandas 등 금지 조건 준수) |

---

## 2. 실행 방법

```bash
python main.py
```

- Windows에서 `python` 명령이 없다면 `py main.py`로 실행합니다.
- `data.json`은 **`main.py`와 같은 폴더**에 있어야 합니다. 저장소에 함께 포함되어 있습니다.
- 다른 데이터 파일로 시험하려면 경로를 인자로 넘깁니다: `python main.py 다른파일.json`

```text

[모드 선택]
1. 사용자 입력 (3x3)
2. data.json 분석

```

## 3. 구현 요약

### 3-1. 데이터 구조: `Matrix`

- n×n 2차원 숫자 배열을 `rows`(리스트의 리스트)로 저장합니다.
- `get(row, col)` / `set(row, col, value)`로 특정 위치의 값을 읽고 씁니다.
- `Matrix.from_rows(rows, expected_size)`가 다음 항목을 검증합니다. 문제가 있으면 원인을 담은 `ValueError`를 발생시킵니다.
  - 2차원 리스트인지
  - 행 수와 열 수
  - 모든 값이 숫자인지 (`bool`, `nan`, `inf` 제외)
- `flatten()`은 길이 N²의 1차원 리스트로 변환합니다. (보너스 최적화용)

### 3-2. MAC 연산

```python
def mac(pattern, kernel):
    total = 0.0
    for i in range(pattern.size):
        for j in range(pattern.size):
            total += a[i][j] * b[i][j]   # 같은 위치끼리 곱해서 누적
    return total
```

- NumPy 없이 **이중 `for` 반복문**으로 직접 구현했습니다.
- 두 행렬의 크기가 다르면 `ValueError`를 발생시킵니다. 결과는 `float`입니다.

### 3-3. 라벨 정규화

data.json은 같은 의미를 서로 다른 표기로 씁니다.
- 정답 칸(`expected`): `+`, `x`
- 필터 이름: `cross`, `x`

프로그램 안에서는 **표준 라벨 `Cross`, `X` 두 가지만** 사용합니다.

| 원본 표기 | 표준 라벨 |
|---|---|
| `+`, `cross` (expected 값, 필터 키) | `Cross` |
| `x` (expected 값, 필터 키) | `X` |

- 비교하기 전에 `strip()`과 `lower()`를 먼저 적용합니다. 그래서 `" CROSS "`, `"X"` 같은 변형도 같은 라벨로 처리됩니다.
- 해석할 수 없는 라벨(예: `circle`)은 해당 케이스를 FAIL로 처리하고 사유를 남깁니다.
- 콘솔 출력과 PASS/FAIL 비교는 모두 표준 라벨 기준입니다.

**정규화하는 이유:** `"+" == "Cross"`는 문자열 비교로는 `False`입니다. 그래서 표기가 다른 것만으로 정답을 오답으로 판정하게 됩니다. 입력 단계에서 한 번만 표준 라벨로 바꿔 두면, 이후 모든 비교 로직이 표기 차이를 신경 쓰지 않아도 됩니다.

### 3-4. 동점 처리 정책 (epsilon)

```python
EPSILON = 1e-9
if abs(score_a - score_b) < EPSILON:   # 동점
    판정 = UNDECIDED (모드 1에서는 "판정 불가")
```

부동소수점은 `0.1`처럼 2진수로 정확히 표현할 수 없는 값을 근사값으로 저장합니다. 그래서 수학적으로 같은 점수도 계산 순서에 따라 `0.9`와 `0.8999999999999999`처럼 아주 조금 달라집니다. `==`나 `>`로 그대로 비교하면 이 미세한 오차가 판정을 좌우합니다. 그래서 **차이가 허용오차(1e-9)보다 작으면 같은 점수로 간주**합니다.

### 3-5. data.json 키 규칙과 스키마 검증

| 항목 | 규칙 | 처리 |
|---|---|---|
| 필터 키 | `size_{N}` (예: `size_13`) | 정규식으로 N을 추출해 해당 크기의 필터로 등록 |
| 필터 값 | `{"cross": N×N, "x": N×N}` | 라벨 정규화 + 크기 검증. 실패하면 그 크기의 모든 패턴을 사유와 함께 FAIL 처리 |
| 패턴 키 | `size_{N}_{idx}` (예: `size_13_2`) | 키에서 N을 추출해 `size_N` 필터를 선택 |
| 패턴 값 | `{"input": N×N, "expected": "+"/"x"}` | 라벨 정규화, 크기 일치 검증 |

**스키마 오류가 있어도 프로그램은 멈추지 않습니다.** 해당 케이스만 FAIL로 처리하고 원인 메시지를 남긴 뒤 다음 케이스로 넘어갑니다.

### 3-6. 성능 측정 방식

- `time.perf_counter()`로 **MAC 함수 호출 구간만** 측정합니다. 입력, 출력, 파일 읽기 시간은 제외합니다.
- 크기마다 **10회 반복한 평균(ms)** 을 출력합니다. 측정 전에 1회 실행(워밍업)해서 첫 호출의 일회성 비용도 뺍니다.
- 측정 데이터
  - 5×5, 13×13, 25×25: data.json의 Cross 필터와 패턴 생성기로 만든 X 패턴을 사용합니다.
  - 3×3: data.json에 3×3 데이터가 없어서 필터와 패턴 모두 생성기로 만든 것을 사용합니다.
- 표에는 `크기(N×N) / 평균 시간(ms) / 연산 횟수(N²)`가 들어갑니다.

### 3-7. 보너스

| 보너스 | 구현 |
|---|---|
| 1차원 배열 최적화 | `flatten()`으로 N×N을 길이 N²의 1차원 리스트로 바꾼 뒤 `mac_flat()`으로 단일 반복문 MAC을 수행합니다. 모드 2에서 같은 입력과 같은 반복 횟수로 2차원/1차원 시간을 비교합니다. 두 방식의 점수가 같은 것도 검증했습니다. |
| 패턴 생성기 | `generate_cross(N)`은 가운데 행과 열을, `generate_x(N)`은 두 대각선을 1로 채웁니다. 모드 3에서 생성 패턴을 필터로 재사용해 판정하고, 성능 분석(3×3 측정)에도 재사용합니다. |

### 5-1. 판정 결과 요약

| size_5_2 | 십자가 | 8.9 | 0.1 | Cross | Cross | PASS |
| size_13_1 | X | 0.3 | 14.700000000000008 | X | X | PASS |
| size_13_2 | 십자가 | 7.499999999999997 | 7.5 | UNDECIDED | Cross | **FAIL** |
| size_25_1 | X | 4.9 | 4.899999999999999 | UNDECIDED | X | **FAIL** |

**총 6개 / 통과 3개 / 실패 3개**

### 5-2. 실패 원인 분석

실패 원인은 세 갈래로 나눠 점검했습니다. **데이터/스키마 문제, 로직 문제, 수치 비교 문제**입니다.

**① 데이터/스키마 문제인가? → 스키마는 정상, 필터 가중치 설계가 원인입니다.**

모든 키가 `size_{N}`과 `size_{N}_{idx}` 규칙을 지키고, 모든 배열이 N×N이며, expected 라벨(`+`, `x`)도 정상적으로 정규화됩니다. 6개 패턴의 0이 아닌 칸을 분석해 보니 정확한 십자가 3개와 정확한 X 3개였습니다. 입력 패턴 자체에도 문제가 없습니다.

문제는 **필터 가중치**입니다. 실패한 3개 크기의 필터는 모두 **십자가와 X가 공통으로 지나가는 가운데 한 칸에 비정상적으로 큰 가중치**가 들어 있습니다. 그래서 상대 모양 필터의 총합과 정확히 같아집니다.

| 케이스 | 필터 구성 | 계산 |
|---|---|---|
| size_5_1 (X 패턴) | Cross 필터: 가운데 `0.9`, 나머지 8칸 `1.0` / X 필터: 9칸 모두 `0.1` | X 패턴은 Cross 필터와 가운데 한 칸만 겹침 → `0.9`, X 필터 → `0.1 × 9 = 0.9` |
| size_13_2 (십자가 패턴) | Cross 필터: 25칸 모두 `0.3` / X 필터: 가운데 `7.5`, 나머지 24칸 `0.3` | 십자가 패턴 → Cross 필터 `0.3 × 25 = 7.5`, X 필터는 가운데만 겹침 → `7.5` |
| size_25_1 (X 패턴) | Cross 필터: 가운데 `4.9`, 나머지 48칸 `1.0` / X 필터: 49칸 모두 `0.1` | X 패턴 → Cross 필터 가운데만 겹침 `4.9`, X 필터 `0.1 × 49 = 4.9` |

세 케이스 모두 **수학적으로 두 점수가 완전히 같은(정확한 동점) 데이터**입니다. 필터만으로는 두 모양을 구별할 수 없습니다.

**② 로직 문제인가? → 아닙니다.**

- 같은 프로그램이 나머지 3개 케이스를 정답과 일치하게 판정했습니다.
- 위 표의 손 계산값과 프로그램 출력값이 일치합니다.
- 2차원 MAC과 1차원 MAC의 결과도 모든 케이스에서 같았습니다.
- 라벨 정규화가 빠졌다면 `"+" ≠ "Cross"` 때문에 PASS 3건까지 FAIL이 되었을 것입니다. 정규화 덕분에 PASS 3건이 정상 집계되었습니다.

**③ 수치 비교 문제인가? → 부동소수점 오차가 있지만, epsilon 정책이 이를 올바르게 흡수했습니다.**

수학적으로는 동점이지만 실제 계산값은 `0.9`와 `0.8999999999999999`처럼 1e-16 ~ 1e-15 수준으로 다릅니다.
- `0.1`을 9번 더하는 동안 2진 근사 오차가 쌓였기 때문입니다.
- `0.3 × 24 + …`처럼 누적 순서에 따라 반올림 오차가 달라지기 때문입니다.

epsilon 없이 `>`로만 비교했다면 이 오차가 승부를 가르고, **판정이 세 건 모두 expected와 반대로** 나옵니다.
- size_5_1 → Cross (expected X)
- size_13_2 → X (expected Cross)
- size_25_1 → Cross (expected X)

즉 epsilon이 없으면 "왜 틀렸는지 알 수 없는 오답"이 생깁니다. epsilon을 적용하면 "구별할 수 없는 데이터"라는 정확한 진단(UNDECIDED)이 나옵니다.

**결론과 개선 방향**
- FAIL 3건은 미션 규칙("동점은 UNDECIDED, 판정이 expected와 다르면 FAIL")을 그대로 지킨 결과입니다. 프로그램 오류가 아닙니다.
- 근본 원인은 **필터 가중치 데이터**입니다. 예를 들어 가운데 칸의 과도한 가중치를 다른 칸과 같은 값으로 맞추면 해결됩니다.
  - size_13의 X 필터 가운데를 `7.5` → `0.3`으로 바꾸면, 십자가 패턴의 X 점수는 `0.3`이 되고 Cross 점수 `7.5`가 명확히 앞섭니다.
- 과제 데이터는 수정하지 않았습니다. 판정 규칙을 데이터에 맞춰 바꾸는 것(예: 동점이면 expected로 처리)은 테스트를 통과시키기 위한 조작이라 적용하지 않았습니다.

### 5-3. 시간 복잡도 분석

**MAC 1회의 연산량은 N²입니다.** N×N 행렬의 모든 칸(N²개)마다 곱셈 1번과 덧셈 1번을 정확히 한 번씩 수행합니다. 이중 반복문이 바깥 N번 × 안쪽 N번 돌기 때문입니다. 따라서 시간 복잡도는 **O(N²)** 입니다. 크기가 2배가 되면 연산은 4배가 됩니다.

| 크기 | 연산 횟수(N²) | 3×3 대비 연산 비율 | 측정 시간(ms, 10회 평균) | 3×3 대비 시간 비율 |
|---|---|---|---|---|
| 3×3 | 9 | 1.0배 | 0.0009 | 1.0배 |
| 5×5 | 25 | 2.8배 | 0.0017 | 1.9배 |
| 13×13 | 169 | 18.8배 | 0.0100 | 11.1배 |
| 25×25 | 625 | 69.4배 | 0.0484 | 53.8배 |

- **N²에 비례해 증가합니다.** 5×5 → 25×25에서 연산은 25배, 시간은 약 28배 늘었습니다. 연산 횟수와 시간이 같은 비율로 커집니다.
- **작은 크기에서는 비율이 N²보다 작게 나옵니다.** 3×3은 연산이 9번뿐이라, 함수 호출·반복문 준비 같은 **고정 비용**이 전체 시간의 큰 부분을 차지하기 때문입니다. 크기가 커질수록 고정 비용의 비중이 줄어 N² 비례에 가까워집니다.
- **10회 평균은 μs(마이크로초) 단위라 측정 잡음이 큽니다.** 그래서 반복 횟수를 1,000회로 늘려 한 칸당 시간을 따로 확인했습니다. 실행마다 값은 조금씩 달라집니다.

  | 크기 | N² | 1회 평균(ms) | 한 칸당 시간(ns) |
  |---|---|---|---|
  | 3×3 | 9 | 0.00064 | 71.2 |
  | 5×5 | 25 | 0.00143 | 57.4 |
  | 13×13 | 169 | 0.00793 | 46.9 |
  | 25×25 | 625 | 0.02970 | 47.5 |
  | 51×51 | 2,601 | 0.11135 | 42.8 |
  | 101×101 | 10,201 | 0.46166 | 45.3 |

  한 칸당 시간이 크기와 상관없이 **약 45ns로 일정하게 수렴**합니다. 이것이 전체 시간이 `상수 × N²`, 즉 O(N²)라는 직접적인 근거입니다.
- **보너스: 1차원 배열 최적화**
  - 2차원 접근 `a[i][j]`는 매번 "바깥 리스트에서 행을 꺼낸 뒤, 다시 열을 꺼내는" 2단계 조회를 합니다.
  - 1차원 접근 `a[k]`는 한 번만 조회하고 반복문도 하나라 반복 관리 비용이 줄어듭니다.
  - 같은 입력으로 여러 번 측정해 보니 **대체로 약 30~45% 빨라졌습니다.**
    - 측정 시간이 μs 단위라 실행할 때마다 차이가 큽니다.
    - 5회 측정 중 한 번은 25×25에서 단축 폭이 약 5%에 그쳤습니다. 다른 프로그램의 영향 같은 측정 잡음으로 보입니다.
  - 다만 연산 횟수는 여전히 N²이므로 **시간 복잡도는 O(N²) 그대로입니다.** 상수 배만 줄어든 최적화입니다.
- **NPU와의 연결**
  - CPU에서 Python 반복문으로 계산하면 N²개의 곱-합을 하나씩 순서대로 처리합니다.
  - 실제 AI 모델은 수백×수백 크기의 필터를 수천 개 사용하므로, 이 방식으로는 감당할 수 없습니다.
  - NPU는 수천 개의 MAC 유닛으로 이 곱셈들을 **동시에(병렬로)** 처리해서, 같은 O(N²) 작업을 훨씬 짧은 시간에 끝냅니다.
